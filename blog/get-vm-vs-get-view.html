Get-VM or Get-View? Choosing the Right PowerCLI Cmdlet

By RMG LabsNovember 21, 20265 min read

Sooner or later every PowerCLI user meets the same question: should this report use Get-VM or Get-View? Both list virtual machines, and on a small lab they feel identical. On an inventory with thousands of VMs the difference can be the gap between a script that finishes while you pour coffee and one that you leave running over lunch. This article explains what each cmdlet does, when to pick it and how to measure the difference yourself.

What Get-VM Gives You

Get-VM is the friendly option. It returns PowerCLI VirtualMachine objects with tidy, easy-to-read properties such as Name, PowerState, NumCpu, MemoryGB, VMHost and ProvisionedSpaceGB. Those objects also plug straight into the rest of PowerCLI, so you can pipe them into Get-Snapshot, Get-HardDisk, Get-Tag or Stop-VM without thinking about it. For everyday tasks, a few dozen VMs and anything that changes a VM afterwards, Get-VM is the right and most readable choice.

What Get-View Gives You

Get-View returns the raw vSphere API object behind the VM. Its property names are the official API names, such as Runtime.PowerState, Config.Hardware.NumCPU and Config.Hardware.MemoryMB, and its values are less polished: power state comes back as poweredOn, memory in megabytes. The reward is control. You choose exactly which properties to fetch with -Property and which objects to return with -Filter, so vCenter does the narrowing and you only transfer the data you need.

Why the Speed Differs

Get-VM builds a rich object for every VM and works out many convenience properties for you. Get-View with a short property list skips most of that. When you only need a handful of fields from a large inventory, asking for just those fields is usually much faster and lighter on vCenter. Exact timings depend on your environment, so measure rather than assume. The script below does that for you.

Try Both Side by Side

This read-only script runs the same simple VM listing both ways, times each and shows a few rows from each. You need the VMware PowerCLI module and a vCenter account with read access. PowerCLI prompts for your username and password, and nothing is stored.

<#
.SYNOPSIS
Times Get-VM against Get-View for a basic VM inventory.
.DESCRIPTION
Lists name, power state, vCPU count and memory for every VM twice,
once with Get-VM and once with Get-View, and shows how long each
took. Read-only: nothing is changed.
.NOTES
Author: James Dougherty (scripty)
Version: 1.0
Updated: 2026-11-21
Category: VMware
Requires: VMware PowerCLI
Credentials: Prompts for your vCenter username and password when it runs
Output: Timing table and sample rows on screen
.PARAMETER Server
vCenter server name or address.
.PARAMETER Top
How many sample rows to show from each method.
.EXAMPLE
.\Compare-VmQuerySpeed.ps1 -Server vcenter.example.local -Top 5
#>
param(
    [Parameter(Mandatory)][string]$Server,
    [int]$Top = 5
)

# No credentials are stored in this script: PowerCLI asks for them.
Connect-VIServer -Server $Server | Out-Null

# Method 1: Get-VM (friendly objects, more work per VM)
$t1 = Measure-Command {
    $script:viaVm = Get-VM | ForEach-Object {
        [pscustomobject]@{
            Name       = $_.Name
            PowerState = [string]$_.PowerState
            NumCpu     = $_.NumCpu
            MemoryGB   = [math]::Round($_.MemoryGB, 1)
        }
    }
}

# Method 2: Get-View (only the properties we ask for; templates excluded)
$t2 = Measure-Command {
    $script:viaView = Get-View -ViewType VirtualMachine `
        -Property Name, Runtime.PowerState, Config.Hardware.NumCPU, Config.Hardware.MemoryMB `
        -Filter @{ "Config.Template" = "false" } | ForEach-Object {
        [pscustomobject]@{
            Name       = $_.Name
            PowerState = [string]$_.Runtime.PowerState
            NumCpu     = $_.Config.Hardware.NumCPU
            MemoryGB   = [math]::Round($_.Config.Hardware.MemoryMB / 1024, 1)
        }
    }
}

[pscustomobject]@{ Method = "Get-VM";   Seconds = [math]::Round($t1.TotalSeconds, 1); VMs = @($viaVm).Count },
[pscustomobject]@{ Method = "Get-View"; Seconds = [math]::Round($t2.TotalSeconds, 1); VMs = @($viaView).Count } |
    Format-Table -AutoSize

"--- Get-VM sample ---"
$viaVm | Select-Object -First $Top | Format-Table -AutoSize
"--- Get-View sample ---"
$viaView | Select-Object -First $Top | Format-Table -AutoSize

Disconnect-VIServer -Server $Server -Confirm:$false

Reading the Results

Both methods should report the same VM count and similar values; only the speed and the raw formatting differ. Notice the small clean-up the Get-View branch needs: the power state is a plain string such as poweredOn, memory is converted from megabytes, and templates are excluded with a filter because Get-View returns them while Get-VM does not. On a small lab the timings may be close. Run it against production, or the largest vCenter you can safely read from, to see where the gap opens up.

Common Properties to Know

A few useful Get-View property paths for VMs: Runtime.PowerState for power state, Config.GuestFullName for the configured guest operating system, Config.Hardware.NumCPU and Config.Hardware.MemoryMB for sizing, and Guest.ToolsStatus for VMware Tools health. On the Get-VM side, look at PowerState, NumCpu, MemoryGB, VMHost, Folder and ProvisionedSpaceGB. Run Get-VM | Get-Member or Get-View -ViewType VirtualMachine | Get-Member to browse everything else.

A Simple Rule of Thumb

Use Get-VM when readability matters, the inventory is modest or you plan to pipe the result into another PowerCLI cmdlet. Reach for Get-View when you are building a read-only report over a large inventory and only need a few properties. A handy middle path is to find objects with Get-View and convert only the ones you need with Get-VIObjectByVIView when you must act on them. If any step changes a VM, use -WhatIf first so the change can be previewed. For a complete read-only example in the same spirit, see our datastore capacity report.
