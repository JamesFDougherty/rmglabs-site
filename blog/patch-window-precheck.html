Before the Patch Window: A Read-Only PowerCLI Maintenance Pre-Check

By RMG LabsNovember 28, 20265 min read

Patch night usually starts the same way: you put the first ESXi host into maintenance mode and watch the task. If every virtual machine moves off cleanly, the evening goes to plan. If one will not move, the progress bar sits still while you hunt for the reason. Many of those reasons can be spotted days earlier. A short read-only PowerCLI pre-check gives you a list to work through during business hours instead of at midnight.

Why Maintenance Mode Stalls

A host cannot finish entering maintenance mode while powered-on VMs are still running on it. With DRS set to Fully Automated, vSphere can move them for you. Broadcom notes that with DRS in Manual or Partially Automated mode, or turned off, the task can sit waiting until the VMs are migrated by hand or the setting is changed. Individual VMs can also hold things up. A VMware Tools installer left mounted can cause a migration to fail. Connected CD/DVD media that the destination host cannot reach, disks on storage only one host can see, passthrough hardware and strict placement rules all deserve a look too.

What the Script Checks

  • Whether DRS is enabled on the cluster, and its automation level.
  • Enabled must rules that tie VMs to, or keep them away from, groups of hosts.
  • Powered-on VMs with the VMware Tools installer mounted.
  • Connected CD/DVD drives, showing the ISO path or device where available.
  • VMs using a datastore that does not report access from multiple hosts.
  • VMs with a PCI passthrough or vGPU device.

The Script

You need the VMware PowerCLI module and a vCenter account with read access. PowerCLI prompts for your username and password when it connects, and nothing is stored. Save the script as Get-PatchWindowPreCheck.ps1 and give it your vCenter address and the exact cluster name. It only reads: it does not disconnect drives, move VMs or change DRS.

<#
.SYNOPSIS
Finds common things that can stall ESXi maintenance mode in a cluster.
.DESCRIPTION
Checks the cluster DRS setting and required VM-to-host rules, then looks
at each powered-on VM for a mounted VMware Tools installer, a connected
CD/DVD drive, disks or files on a non-shared datastore and PCI
passthrough devices. Optionally exports the findings to CSV. Read-only:
nothing is changed.
.NOTES
Author: James Dougherty (scripty)
Version: 1.0
Updated: 2026-11-28
Category: VMware
Requires: VMware PowerCLI
Credentials: Prompts for your vCenter username and password when it runs
Output: Text and tables on screen, optional CSV file
.PARAMETER Server
vCenter server name or address.
.PARAMETER ClusterName
Exact name of the cluster you plan to patch.
.PARAMETER CsvPath
Optional path for a CSV copy of the VM findings.
.EXAMPLE
.\Get-PatchWindowPreCheck.ps1 -Server vcenter.example.local -ClusterName Lab01
#>
param(
    [Parameter(Mandatory)][string]$Server,
    [Parameter(Mandatory)][string]$ClusterName,
    [string]$CsvPath
)

# No credentials are stored in this script: PowerCLI asks for them.
Connect-VIServer -Server $Server -ErrorAction Stop | Out-Null

try {
    $cluster = Get-Cluster -Name $ClusterName -ErrorAction Stop |
        Select-Object -First 1

    Write-Host "Cluster: $($cluster.Name)"
    Write-Host "DRS enabled: $($cluster.DrsEnabled)"
    Write-Host "DRS automation level: $($cluster.DrsAutomationLevel)"

    Write-Host "Enabled 'must' VM-to-host rules:"
    Get-DrsVMHostRule -Cluster $cluster |
        Where-Object { $_.Enabled -and "$($_.Type)" -like 'Must*' } |
        Format-Table Name, Type, VMGroup, VMHostGroup -AutoSize | Out-Host

    # Datastores that only one host can reach
    $localStores = @{}
    Get-VMHost -Location $cluster | Get-Datastore |
        Where-Object { $_.ExtensionData.Summary.MultipleHostAccess -eq $false } |
        ForEach-Object { $localStores[$_.Id] = $_.Name }

    $vms = Get-VM -Location $cluster |
        Where-Object { $_.PowerState -eq 'PoweredOn' }

    $report = foreach ($vm in $vms) {
        $findings = @()

        if ($vm.ExtensionData.Runtime.ToolsInstallerMounted) {
            $findings += 'VMware Tools installer is mounted'
        }

        foreach ($cd in Get-CDDrive -VM $vm) {
            if ($cd.ConnectionState.Connected) {
                $source = @($cd.IsoPath, $cd.HostDevice, $cd.RemoteDevice) |
                    Where-Object { $_ } | Select-Object -First 1
                $findings += "Connected CD/DVD: $source"
            }
        }

        foreach ($id in $vm.DatastoreIdList) {
            if ($localStores.ContainsKey($id)) {
                $findings += "Uses non-shared datastore: $($localStores[$id])"
            }
        }

        $pci = $vm.ExtensionData.Config.Hardware.Device |
            Where-Object { $_ -is [VMware.Vim.VirtualPCIPassthrough] }
        if ($pci) { $findings += 'Has a PCI passthrough or vGPU device' }

        foreach ($finding in $findings) {
            [pscustomobject]@{
                VM      = $vm.Name
                Host    = $vm.VMHost.Name
                Finding = $finding
            }
        }
    }

    if ($report) {
        $report | Sort-Object Host, VM | Format-Table -AutoSize -Wrap | Out-Host
        if ($CsvPath) { $report | Export-Csv -Path $CsvPath -NoTypeInformation }
    }
    else {
        Write-Host 'No VM findings from these checks.'
    }
}
finally {
    Disconnect-VIServer -Server $Server -Confirm:$false
}

Working Through the Findings

Treat each line as a question to answer, not a confirmed fault.

  • Tools installer: check with the system owner that no install or upgrade is still running, then unmount it from the VM’s menu.
  • CD/DVD: an ISO on shared storage may be perfectly fine. If nobody needs it, disconnect it. If someone does, confirm every destination host can reach it.
  • Non-shared datastore: decide ahead of time whether to move the storage, shut the VM down for the window, or leave that host for a separate slot.
  • Passthrough or vGPU: some of these VMs cannot be live migrated, and others can only under specific conditions. Confirm which applies and plan a shutdown with the owner if needed.
  • Must rules: make sure each affected VM still has at least one allowed host while its current host is out.

What It Does Not Cover

A clean result is encouraging, but it is not a guarantee. The script does not test spare capacity, VM-to-VM rules, HA admission control, vMotion networking, CPU compatibility or whether a shared datastore is visible to every host. vSAN clusters have their own data evacuation choices, and your hardware and update tooling may add prechecks that you should run as well.

Make It Part of the Routine

Run the pre-check a few days before the window so owners have time to respond, then run it again on the day to catch anything new. Pair it with the host health report to confirm the other hosts are healthy enough to take the load, and the snapshot report to tidy up old snapshots before changes begin. Saving each CSV with your change ticket also leaves a simple record of what you checked.
